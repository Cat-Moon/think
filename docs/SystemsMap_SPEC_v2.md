## v2.1 改动清单（相对 v2）

1. **确定名称与界面语言**：项目名 Think；界面只做中文，AI 跟随用户使用的语言回复。
2. **确定应用形态**：本地网页应用（小型 Node 服务 + 浏览器打开 localhost），代码分 `core / server / web` 三层，以后可再套 Electron 外壳。
3. **确定图库**：Cytoscape.js（含力导向布局插件）。
4. **补丁确认模型（重要）**：AI 补丁以"幽灵预览"显示在图上，逐项接受或拒绝。**`graph.json` 中不再有 `proposed` 状态**，只存已确认的内容；未被接受的操作记录在 `patches/` 中。种子图本身就是第一个补丁。
5. **用户的直接编辑也走补丁**（`origin: user`，自动接受），版本历史只有一条路径。拖动布局不算版本，单独存放在 `layout.json`。
6. **AI 不分配 ID**：新节点在补丁中使用临时引用（`$a`、`$b`），由代码分配真实 ID。补丁操作新增 `update_node`、`remove_node`、`merge_nodes`、`reverse_edge`、`set_frame`。
7. **"反向"拆成两个按钮**：「极性相反」（+/− 翻转）和「方向反了」（箭头掉头）。
8. **极性允许 `?`（未知）**；含 `?` 边的回路极性显示为"?"，不硬判 R / B。
9. **回路检测范围明确**：只使用 `accepted` 和 `uncertain` 的边；含 `uncertain` 边的回路以虚线显示。算法为按起点去重的 DFS 基本回路枚举（图很小，不需要 Johnson 算法），回路数和搜索步数都设上限。
10. **AI 上下文明确**：每次调用都带上完整当前图、代码算出的回路、被拒绝内容清单、用户自上一轮以来的改动、最近 8 轮对话原文。暂不做摘要。
11. **AI 输出分三种**：`clarify`（澄清问题）/ `patch`（补丁）/ `answer`（只回答，`ops` 可为空）。
12. **代码二次校验 AI 输出**：JSON 结构由 CLI 的 `--json-schema` 保证；引用是否存在、每轮新增不超过 3 个、只问一个问题等规则由代码校验。不通过时附上错误信息重试一次，仍失败则展示给用户，不静默截断。
13. **中性名词检查**：提示词中给出正反例；代码用小词表做"疑似带方向"的提示，只警告、不阻止。
14. **同义变量检测**：MVP 使用"代码标签归一化比较 + AI 输出中的 `possible_duplicates`"，由用户确认合并。不做嵌入相似度。
15. **种子图**：MVP 只调用一次，不做多次采样。
16. **去掉 AI 调用缓存（`cache/`）**；改为把每次调用的完整输入和输出记入 `logs/provider.jsonl`。
17. **以 `versions/` 为准**：`graph.json` 是最新版本的派生副本，可随时重建。
18. **元信息文件改为 JSON**（`workspace.json`、`map.json`），减少依赖。
19. **ClaudeCodeProvider 调用方式已查证并实测**（见第 8 节）。重要：**不能使用 `--bare`**，该模式不读取订阅登录。
20. **用量只显示调用次数和 token 数**，不显示 CLI 返回的美元估算（那是 API 价格估算，订阅用户不按此计费）。
21. **订阅条款结论**写入第 8.3 节；保留 API key provider 的接入可能。
22. **11.3 用户测试改为"只自己使用"**；别人试用的方式以后再讨论（涉及订阅条款）。
23. **延迟表示**：箭头中部的 ‖ 标记。
24. **隐私说明**：首次启动显示一屏说明。
25. **默认模型 sonnet**，界面可切换。
26. **第 12、13 节改为里程碑计划**；M3 完成后暂停，由用户检查种子图质量后再做界面。
27. **第 14 节改为"已决事项"记录**。

## 1. 项目概述

Think 是一个**对话式的 AI 系统思维工具**，供我自己使用。

用户提出一个主题或现象，AI 先给出一张**很小的种子因果图**（几个变量加几条关系），再通过**对话和点按**，和用户一起慢慢完善这张图。图以 graph view 呈现：节点是变量，箭头是因果关系，系统用代码自动找出其中的反馈回路。

### 核心价值

- 让系统思维的上手曲线更平稳：不需要先学会画 CLD 的符号和规则，在对话里自然学会
- 把"思考的过程"留下来：图的每一步演化、每条关系的理由、自己的笔记，都保存在本地文件夹里
- 帮助理解"是什么因素导致现在的局面"，以及"某个因素变了会怎样"（后期通过轻量仿真）

### 与现有产品的关系

已经有人做 AI 辅助的因果回路图（附录 B，未经验证）。Think 的重点不在"能自动画图"，而在**学习体验**：AI 多提问、少给答案；图是用户自己的假设；图的演化历史可回看；每条边带理由。

## 2. 设计原则

1. **图是假设，不是真相。** AI 的输出一律是"建议"，界面上应体现不确定性。
2. **LLM 提结构，代码做计算。** 回路识别、极性判断、图校验、之后的仿真数值，全部由代码完成。LLM 只负责提出建议和解释，不负责计算，也不"预测"结果。
3. **小种子加一个问题。** 种子图 3 到 5 个变量、最多一条回路，同时只问一个最有价值的问题。
4. **AI 不直接改图，只提交补丁。** 补丁由用户逐项确认后才生效。用户自己的编辑也以补丁形式记录。
5. **图的所有权属于用户。** 用户可以随时改、拒绝、反驳。被拒绝的内容保留记录，不会消失。
6. **学习优先于效率。** AI 默认引导思考，而不是代替思考。
7. **不说预测。** 任何仿真结果都标注为"示意"。
8. **数据在本地，格式开放。** 每个主题一个文件夹，使用 JSON / JSONL / Markdown。
9. **争议性主题保持中立。** 有争议的关系标为"有争议"，不替用户站队。
10. **保持简单。** 个人项目，不过度设计，不做商业化相关功能。

## 3. 核心概念

| 概念 | 说明 |
|---|---|
| **Map（主题）** | 一个主题对应一个 Map，保存在一个独立文件夹里，侧边栏里像一条"对话" |
| **Frame（框架）** | Map 的主题、要解释的现象、视角、时间范围 |
| **Node（节点 / 变量）** | 系统中的一个变量。变量名用中性名词（可增可减）：写"房价"，不写"房价上涨" |
| **Edge（边 / 因果关系）** | 从原因到结果的箭头，带极性（`+` / `-` / `?`）、是否有延迟、理由、状态 |
| **Loop（回路）** | 由代码自动检测出的闭环：R（增强）/ B（平衡）/ ?（含未知极性）。不存储为主数据 |
| **Patch（补丁）** | 一组修改操作。AI 补丁需逐项确认；用户补丁自动接受 |
| **Version（版本）** | 每个补丁被（部分）接受后生成一个图的快照 |
| **Turn（对话回合）** | 一条用户或 AI 消息，可关联补丁和版本 |
| **Note（笔记）** | 用户自己写的观察、假设、结论 |
| **Mode（模式）** | 「你先画」（MVP 唯一模式）和「我先想」（第二阶段） |

## 4. 用户流程

```
用户输入主题
   │
   ▼
主题太模糊？ ── 是 ──► AI 回复 kind=clarify：问一个澄清问题
   │ 否                （你想解释的是什么随时间变化的现象？从谁的角度看？时间范围？）
   ▼
AI 回复 kind=patch：种子补丁（set_frame + 3–5 个变量，≤1 条回路）+ 1 个问题
   │
   ▼
┌─► 补丁以幽灵预览显示在图上 → 用户逐项接受 / 拒绝（可全部接受）
│        → 生成新版本 → 代码重新检测回路
│   用户通过对话或点按回应
│     - 点按已有的边：同意 / 极性相反 / 方向反了 / 不同意 / 不确定
│     - 直接编辑：加变量、改名、加边、删除（均记为用户补丁）
│     - 对话：补充变量、质疑关系、问"为什么"
│        │
│        ▼
│   AI 回复：patch（每轮新增 ≤3 个节点或边）或 answer，并附一个问题
└────────┘
随时：回看版本历史、恢复到某个版本、写笔记
```

AI 调用进行中时，图的编辑暂时锁定，避免补丁基于过期版本。

## 5. AI 行为设计

### 5.1 学习导向的行为准则（写入系统提示词）

- 每轮只问**一个**问题，优先问能推动思考的问题，例如："你觉得 A 会影响 B，那反过来呢？""这个影响多久才会显现？""如果这条关系成立，你期待能观察到什么？"
- 提出每条边时附上一句简短理由，并说明是否有其他解释
- 主动提示图里可能缺少的东西：延迟、被忽略的反馈、变量之间的同义重复
- 每轮新增的节点和边合计不超过 3 个（种子图除外：3–5 个变量）
- 变量名使用中性名词，不带"上涨、下降、增加、减少、过多、缺乏"等方向词
- 对不确定的关系明确说"不确定"，极性不确定时使用 `?`
- 不重新提出用户已经拒绝过的内容，除非用户主动要求
- 不自己判断回路极性；需要讨论回路时，使用上下文中由代码算出的回路
- 使用用户使用的语言回复
- 不下结论式断言，除非用户明确要求 AI 直接给出看法

### 5.2 两个模式

- **「你先画」（MVP）**：AI 先给小种子图，用户在此基础上完善
- **「我先想」（第二阶段）**：AI 先不给图，请用户写下他认为最重要的 3 到 5 个变量和关系，再据此画图，最后展示差异

### 5.3 边的置信度（第二阶段）

对同一主题独立生成多次种子图，统计每条边出现的比例作为置信度。它衡量的是"AI 多次生成的一致性"，**不等于现实中是否成立**，界面文案要避免误解。MVP 不做。

### 5.4 AI 的上下文（每次调用，无状态）

每次调用都由代码组装以下内容，不依赖 CLI 的会话历史：

1. 系统提示词（行为准则 + 输出格式说明）
2. Frame：主题、现象、视角、时间范围
3. 当前图的紧凑文本表示（节点 ID 与标签；边的 ID、方向、极性、延迟、状态、理由）
4. **代码算出的回路**列表（如 `R1: n1 → n2 → n1`）
5. **被拒绝的内容清单**（图中 `rejected` 的项 + 补丁中被拒绝的操作，附理由）
6. 用户自上一轮 AI 回复以来的直接改动
7. 最近 8 轮对话原文
8. 用户的新消息

### 5.5 AI 输出格式（structured output）

```json
{
  "kind": "patch",
  "message": "给用户看的说明（为什么提出这些修改）",
  "question": "你觉得利率变化会立刻影响需求吗？",
  "ops": [
    { "op": "add_node", "ref": "$a", "label": "贷款利率", "rationale": "..." },
    { "op": "add_edge", "from": "$a", "to": "n2", "polarity": "-", "delay": false, "rationale": "..." }
  ],
  "possible_duplicates": [ { "a": "n3", "b": "n5", "reason": "可能指同一件事" } ]
}
```

- `kind`：`clarify` / `patch` / `answer`。`clarify` 和 `answer` 的 `ops` 为空
- `question`：恰好一个问题（`answer` 时可以为空）
- 代码校验（第 6 节第 4 条），不通过时附错误信息重试一次

## 6. 代码负责的部分

1. **回路检测**：枚举所有基本回路（按编号依次以每个节点为起点做 DFS，只经过编号不小于起点的节点），只用 `accepted` 和 `uncertain` 的边，且两端节点都是 `accepted`；平行边算作不同的回路；自环算作长度为 1 的回路；上限 200 个，超过时标记"已截断"。回路名 R1 / B1 / ?1 按长度和节点顺序编号，版本之间不保证稳定
2. **回路极性**：沿回路把各边极性相乘。负边个数为偶数为 R，奇数为 B；含 `?` 边为 `?`。**必须由代码完成**
3. **图校验**：重复标签、孤立节点、自环、引用不存在的节点、疑似同义变量（标签归一化后相同或包含）、疑似带方向的变量名（词表警告）
4. **AI 输出校验**：引用的 ID / `$ref` 存在；`$ref` 不重复；每轮新增节点 + 边 ≤ 3（种子补丁：节点 3–5、回路 ≤1）；`question` 只含一个问号；`clarify` / `answer` 时 `ops` 为空
5. **补丁应用**：检查 `base_version` 等于当前版本，否则拒绝；已处理过的补丁不能再处理；分配真实 ID；部分接受时，如果某个新节点被拒绝，依赖它的边自动随之拒绝（并告知用户）；未给出选择的操作视为拒绝；被接受的操作中任何一项不合法，整个补丁都不生效，并指出是第几项。具体规则：
   - `$ref` 只在本补丁内有效，不能重复定义，必须先定义后引用
   - 新变量不能和已有的（未被拒绝的）变量同名（按归一化后的标签比较）
   - `add_edge` 不能指向自己，不能和已有的同向边重复，两端不能是被拒绝的变量
   - `reverse_edge` 后不能和已有的同向边重复
   - `merge_nodes` 后，原来连接两者的边变成自环，置为 `rejected`
   - `update_edge` 把被拒绝的边重新启用时，两端变量必须仍然有效
6. **布局**：Cytoscape 力导向布局；已有节点位置锁定，只为新节点排位；位置存在 `layout.json`
7. **版本管理**：生成快照、计算两版本的差异、恢复到旧版本（恢复本身也生成一个新版本）
8. 第三阶段起：仿真数值计算（见第 10 节）

## 7. 数据结构

### 7.1 图（graph.json，与最新版本快照相同）

```json
{
  "schema_version": 1,
  "version": "v003",
  "frame": {
    "topic": "房价为什么持续上涨",
    "phenomenon": "房价随时间持续上升",
    "perspective": "城市居民",
    "time_horizon": "20 年"
  },
  "nodes": [
    { "id": "n1", "label": "房价", "status": "accepted", "origin": "user", "note": "" }
  ],
  "edges": [
    {
      "id": "e1", "from": "n2", "to": "n1",
      "polarity": "+", "delay": false,
      "status": "accepted", "origin": "ai",
      "rationale": "需求增加会推高成交价格",
      "contested": false, "confidence": null, "note": ""
    }
  ]
}
```

- 节点 `status`：`accepted` / `rejected`
- 边 `status`：`accepted` / `uncertain` / `rejected`
- `rejected` 的项保留在图中，界面默认隐藏，可切换显示；不参与回路检测。节点被拒绝时，与它相连的边视为不参与计算
- `origin`：`user` 或 `ai`
- `polarity`：`+` / `-` / `?`
- ID 由代码分配：节点 `n1, n2, …`，边 `e1, e2, …`，不复用
- 节点类型暂时只有普通变量；第三阶段引入 `stock` / `flow` / `parameter`

### 7.2 补丁操作

| 操作 | 字段 | 说明 |
|---|---|---|
| `set_frame` | `phenomenon?, perspective?, time_horizon?` | 设置或修改 Frame（种子补丁使用） |
| `add_node` | `ref, label, rationale?` | `ref` 形如 `$a`，代码分配真实 ID |
| `update_node` | `id, label?, note?` | 改名或改笔记 |
| `remove_node` | `id, reason?` | 置为 `rejected`（保留记录） |
| `merge_nodes` | `keep, merge, label?` | 把 `merge` 的边改接到 `keep`，`merge` 置为 `rejected` |
| `add_edge` | `from, to, polarity, delay?, rationale, contested?` | `from` / `to` 可以是已有 ID 或本补丁的 `$ref` |
| `update_edge` | `id, polarity?, delay?, status?, rationale?, note?, contested?` | |
| `reverse_edge` | `id` | 箭头掉头 |
| `remove_edge` | `id, reason?` | 置为 `rejected`（保留记录） |

### 7.3 点按回应对应的用户补丁

| 用户操作 | 生成的操作 |
|---|---|
| 同意 | `update_edge { status: "accepted" }` |
| 极性相反 | `update_edge { polarity: 翻转 }`（`?` 时让用户选 + 或 −） |
| 方向反了 | `reverse_edge` |
| 不同意 | `remove_edge { reason? }` |
| 不确定 | `update_edge { status: "uncertain" }` |

### 7.4 补丁文件（patches/p004.json）

```json
{
  "patch_id": "p004",
  "base_version": "v003",
  "origin": "ai",
  "created_at": "2026-11-08T14:00:00Z",
  "turn_id": "t007",
  "ops": [ ],
  "message": "…",
  "question": "…",
  "possible_duplicates": [],
  "resolution": {
    "resolved_at": "2026-11-08T14:02:00Z",
    "decisions": [
      { "op_index": 0, "decision": "accepted" },
      { "op_index": 1, "decision": "rejected", "reason": "我觉得关系不大", "auto": false }
    ],
    "result_version": "v004"
  }
}
```

- 尚未处理的补丁 `resolution` 为 `null`
- 全部拒绝时 `result_version` 为 `null`（不生成新版本）
- `auto: true` 表示因依赖的新节点被拒绝而自动拒绝

### 7.5 版本文件（versions/v004.json）

```json
{
  "version": "v004",
  "parent_version": "v003",
  "patch_id": "p004",
  "created_at": "…",
  "graph": { }
}
```

`v000` 是创建 Map 时的空图。

**历史只增不改**：版本文件一旦写入，就永远不会被修改或删除；新版本必须紧接在最新版本之后（`parent_version` 是最新版本，编号 +1），存储层会拒绝覆盖已有的版本文件或插入不连续的版本。

**恢复旧版本也是生成一个新版本**：例如当前是 v005，恢复到 v002，会生成 v006（`parent_version: v005`，`patch_id: null`），内容是 v002 的图；v003–v005 原样保留，之后仍可再恢复到它们。当前图中有、旧版本中没有的节点和边，在 v006 中以 `rejected` 状态保留，保证 ID 不复用，被放弃的内容也有记录。

### 7.6 争议性主题

- 对有争议的边设置 `contested: true`，并在界面上标注
- 种子图应尽量覆盖不同立场认可的变量，而不是只呈现一种叙事
- 双方观点的详细展示放在第二阶段

## 8. AI 连接层（AgentProvider）

```ts
interface AgentProvider {
  name: string;
  healthCheck(): Promise<ProviderStatus>;          // 是否已登录、是否可用
  complete(req: LLMRequest): Promise<LLMResponse>; // 单次、无状态调用
}
```

MVP 有两个实现：`FakeProvider`（测试和界面开发用，返回预设结果）和 `ClaudeCodeProvider`。以后可新增 API key provider。

### 8.1 ClaudeCodeProvider 调用方式（2026-11-08 查阅官方文档，并在本机 CLI 2.1.158 实测）

```
claude -p --output-format json
       --json-schema '<AI 输出的 JSON Schema>'
       --system-prompt '<Think 的系统提示词>'
       --tools ""                  # 禁用全部内置工具
       --strict-mcp-config         # 不加载任何 MCP 服务器
       --setting-sources ""        # 不加载用户 / 项目设置
       --no-session-persistence    # 不保存会话
       --model sonnet              # 默认 sonnet，可切换
```

- 提示词内容通过 **stdin** 传入（避免 Windows 命令行长度和中文转义问题）
- 子进程的工作目录设为一个空的临时目录
- 结果在返回 JSON 的 `structured_output` 字段中（已按 schema 校验）。AI 拒绝等情况下该字段不存在，代码需处理
- 其他有用字段：`is_error`、`subtype`、`api_error_status`、`result`、`usage`、`modelUsage`、`duration_ms`
- 结构化输出在内部占用一轮，**不要设置 `--max-turns 1`**
- **不要使用 `--bare`**：该模式不读取 OAuth 订阅登录，只接受 API key
- 登录检查：`claude auth status`（输出 JSON，未登录时退出码 1）
- 实测延迟：haiku 约 9 秒；sonnet 更慢。界面需显示"思考中"、可以取消，失败后不丢失用户输入

### 8.2 其他要求

- 启动时检测 `ANTHROPIC_API_KEY`：`-p` 模式下只要设置了该变量就会改用 API key 计费。检测到时警告用户，并从子进程环境中移除
- 绝不读取、复制或存储 CLI 的凭证文件
- 每次调用的完整输入、输出、用时、token 用量记入 `logs/provider.jsonl`
- 界面显示调用次数和 token 数（不显示美元估算）
- 额度用尽或出错时：提示用户，保留输入，可稍后重试
- 首次使用时显示隐私说明（第 9.3 节）

### 8.3 订阅条款结论（2026-11-08 查阅，非法律意见）

- 官方法律合规页：订阅 OAuth 用于"Claude Code 及其他 Anthropic 原生应用的正常使用"；不允许第三方开发者把 Claude.ai 登录接入自己的应用或代表其用户使用订阅凭证；但"不妨碍终端用户用自己的订阅登录**未修改的** Claude Code 程序"
- 消费者条款第 3 节第 7 条：除 API key 或另有明确许可外，不得通过"自动化或非人工方式"访问服务
- 订阅有 5 小时窗口限额和每周限额，与 Claude 网页版共用；标称额度假设"普通的个人使用"
- **结论**：自己使用、调用本机未修改的 `claude`、不接触凭证、调用量接近手动聊天，是最接近例外条款的用法，但脚本调用仍处于灰色地带。因此：只自己使用；保留 API key provider 的接入可能；给别人使用的方式以后再讨论

### 9.4 工作区与文件夹结构

工作区默认在 `~/Documents/Think`，可通过环境变量 `THINK_WORKSPACE` 修改。

```
Workspace/
  workspace.json                   # 工作区设置：schema_version、默认模型、是否看过隐私说明
  maps/
    2026-11-08_房价为什么持续上涨/   # 一个主题 = 一个文件夹
      map.json                     # schema_version、标题、创建 / 更新时间、父 Map（分叉来源）、是否归档
      graph.json                   # 最新版本的图（派生副本）
      layout.json                  # 节点位置
      versions/
        v000.json                  # 空图
        v001.json
      patches/
        p001.json                  # 补丁及处理结果
      conversation.jsonl           # 对话记录（每条可关联 patch / version）
      notes.md                     # 用户的笔记
      exports/
      logs/
        provider.jsonl             # AI 调用记录（输入、输出、用时、用量）
```

规则：
- **文件夹名**：`本地日期_主题`。保留中文；全角字母数字转半角；去掉 Windows 非法字符（`<>:"/\|?*` 和控制字符），空白变成 `-`；不以点或空格结尾；避开 Windows 保留名（CON、NUL、COM1 等，前面加 `_`）；最长 40 个字符（按字符截断，不切坏中文）；重名时加 `-2`、`-3`（不区分大小写）
- **原子写入**：所有 JSON 和 Markdown 文件都先写同目录下的临时文件，再改名覆盖，中途崩溃不会留下写了一半的文件
- **`conversation.jsonl` 只追加**：读取时逐行解析，坏行（如崩溃时写了一半的最后一行）跳过并报告；追加前如果最后一行不完整，先补一个换行，新行不会和残行粘在一起
- **补丁文件**只允许从"未处理"更新为"已处理"一次，`ops` 等内容不能改
- **当前版本**是 `versions/` 中编号最大的版本（`map.json` 不另存当前版本，避免两处不一致）；`graph.json` 缺失、损坏或落后时自动从最新版本重建
- **处理补丁时先写版本、再写补丁**：中途崩溃时补丁仍显示未处理，但再次处理会因为版本已变而被拒绝，不会重复应用
- **迁移入口**：打开 Map 前检查 `map.json` 的 `schema_version`；旧了就按迁移步骤逐步升级（目前为空），比程序新则拒绝打开，避免旧程序改坏新格式的数据
- **完整性检查**：版本编号连续、`parent_version` 链正确、版本与补丁互相引用一致、对话引用的补丁和版本存在、`graph.json` 与最新版本一致
- 复制（分叉）一个 Map：新 Map 的 v000 是空图，v001 是源 Map 最新版本的内容；复制 `layout.json` 与 `notes.md`；在 `map.json` 中记录 `parent`
- 布局写入不算版本，也不更新 `updated_at`
- 测试一律使用临时目录；测试期间 `THINK_WORKSPACE` 被指向临时目录，保证碰不到真实工作区
- 工作区数据和日志不进 git 仓库（见 `.gitignore`）

### 9.5 conversation.jsonl 每行

```json
{ "turn_id": "t007", "role": "ai", "kind": "patch", "text": "…", "question": "…", "patch_id": "p004", "created_at": "…" }
```

`role`：`user` / `ai` / `system`（如"已恢复到 v002"）。

## 10. 仿真路线（分阶段，轻量优先）

**结论：最终需要仿真，但做成轻量版，且放在对话式因果图验证之后。**

原因：系统思维的核心是"结构产生行为"。只有图，用户看不到行为，也无法检验自己的想法；有了仿真，"先猜后揭示"才有东西可揭示。

风险：从定性图到定量模型是系统动力学里最难的一步。若让 AI 编数字再画出光滑曲线，用户容易把它当成预测。因此第三阶段（草图仿真）遵循：

1. **LLM 提结构和方程，代码负责计算。** 方程对用户可见、可修改
2. 引入存量（stock）和流量（flow）；数值用**相对刻度**（如 0 到 1）
3. 只关注**行为的形状**（增长、衰减、过冲后崩溃、振荡、S 形、稳定）
4. 界面上明确标注"示意，不是预测"
5. 加入**敏感度检查**：晃动参数，看行为形状是否改变
6. 数值积分器用简单方法（欧拉法或龙格库塔）
7. 结合「先猜后揭示」：运行前让用户先猜行为形状

### M3 待办事项（2026-11-08 记录，M3 时一并处理）

1. **回路字眼检查**：代码检查 AI 的 `message`、`question` 和每条 `rationale` 中是否出现"回路""反馈""循环""增强""平衡""loop""feedback""reinforcing""balancing"等字眼，出现就警告（AI 不应自己判断回路，见原则 2）

## 附录 A：早期 LifeSim 仿真构想（摘要，留待第四阶段）

早期设计是一个基于智能体的人生仿真系统，主要想法如下，未来做个体仿真时可复用：

- **实体与阶段**：每个实体（人、公司等）有静态背景和动态状态，经历若干阶段
- **两类事件**：概率型（按概率抽样，概率受状态和世界影响）和选择型（由"中枢"生成选项，Agent 选择）
- **世界层**：所有实体共享的世界状态（经济、政策、资源、重大事件），与个体双向影响；有限资源由中枢分配；全局时钟按年推进
- **两档引擎**：精细模式（LLM 逐个决策）和宏观模式（用 LLM 生成决策概率表后抽样，大规模、低成本）
- **解析模式与蒙特卡洛**：简单、离散、无反馈的配置可直接用概率相乘精确计算分布；复杂情形用多次抽样。两者可以互相验证
- **数据包**：概率与规则放在可替换的数据包里，娱乐包与真实数据包共用同一引擎；族群只作为背景标签，不直接决定结果
- **可复现与分叉**：随机种子、反事实分支、同一种子下比较基线与干预
- **归因**：通过扰动起点、逐个去除因素，分辨结果是偶然还是必然，并排出因素的重要性
- **注意事项**：用 LLM 决策时要防止它因为知道历史而往真实历史靠；选择型事件的决策应可审计，可转成概率表
